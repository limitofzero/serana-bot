# What serana is trying to be

The project follows the model set out in Nikita Pastukhov's Habr article [«Вам не нужен
OpenClaw — напишите свой»](https://habr.com/ru/articles/1029326/) (14 May 2026). This file
records the parts we adopted and where we stand on each.

Like `reference-notes.md`, this is data rather than doctrine: the article argues a position
under its own constraints, and where we diverge the reason is written down.

## The thesis

> **Agent = LLM + Harness.**

The model is a stateless HTTP endpoint: JSON in, JSON out. It has no memory, no clock, no
ability to do anything. Everything that makes it useful — deciding what goes into the
request, giving it tools, remembering across calls, running it on a schedule, keeping it
from being talked into something — is ordinary software around it. The article's claim is
that writing that software for one specific job is not much harder than a CRUD app, and
that a purpose-built agent beats a universal one on both cost and safety.

That is the whole reason this repo exists rather than a config file for someone else's
agent framework.

## The six parts of the harness

The article breaks the harness into six concerns. They are the project's roadmap, in
roughly this order:

| Part | What it is | Where serana is |
| --- | --- | --- |
| **Context management** | The conversation is a growing array of messages. Every turn re-sends all of it, so it costs money and eventually stops fitting. Compress, summarise or archive. | Ports exist — `Conversation` enforces strict role alternation and a byte-stable system prompt (`domain/conversation.rs`), `ConversationRepository` persists it. No turn loop and no compaction yet. |
| **Tools** | Functions with a JSON schema that the model chooses to call. The failure mode is *overtooling*: too many definitions and the model picks worse. | `Tool`, `ToolSpec`, `ToolRegistry` in the domain; schemas generated by `schemars`, never hand-written. Reminders already use one (`schedule_reminder`). No registry is wired into a loop yet. |
| **Memory** | Not a special mechanism — a repository plus a few tools for reading, writing and searching it. Files today, a vector index later. | `MemoryRepository`, and `EmbeddingProvider` / `Retriever` alongside it so the vector implementation has somewhere to go. No implementation yet. |
| **Subagents** | Isolated agent instances for subtasks, so intermediate steps never enter the parent's context. | Not started. |
| **Skills** | Instructions plus scripts, loaded into context on demand rather than sitting there permanently. | Not started. |
| **Scheduling** | Cron-like registration: the agent calls *itself* with a prompt at an interval, so it can watch for conditions instead of only answering. | **This is what works today.** See `reminders.md`. |

## The principles we took

- **Specialisation over universality.** One assistant for one person, not a framework.
  Concretely: the reminder parser is a single-purpose extraction call against a small model
  with `temperature = 0`, not a general agent asked to be careful.
- **Least privilege.** The bot answers only the ids in `SERANA_ALLOWED_USER_IDS`, and an
  empty list means nobody. A leaked bot token with an open allowlist would take instructions
  from, and spend tokens for, whoever found it.
- **Context efficiency.** Nothing is re-rendered into the system prompt mid-conversation —
  the prompt-caching invariant in `reference-notes.md` §2 is the same argument with a price
  tag attached. Retrieved memories arrive as tool results.
- **Isolation.** Deferred with subagents, but the port shapes already assume a turn can be
  run with a different provider, registry and conversation than its parent.
- **Sandboxing.** The whole thing deploys as a container with a single named volume; §5 of
  the engineering rules keeps it that way.
- **Model output is untrusted input.** The article frames this as prompt injection; we take
  the stronger version — the model's *own* output is parsed and validated, never assumed.
  `services/reminders/parse.rs` exists because a plausible hallucination would otherwise
  become a reminder that fires on the wrong day.

## Where we diverge

- **Rust, not Python.** The article's examples are Python and lean on import-time
  registration. We get the same separation from crate boundaries, and cargo checks it.
- **Two frontends from day one.** The article assumes one surface. We have a CLI and a
  Telegram bot, which is why `serana-app` exists: a command, a reply and a line of wiring
  belong to both, and anything that ends up in one binary drifts out of the other.
- **Scheduling before chat.** The article presents scheduling last, as a capability an agent
  gains. We built it first, because a reminder is the smallest useful thing that needs the
  whole spine — a model call, validated output, storage, and a background loop — and it is
  worth having before the loop it will eventually live inside.
